# 三类"假验证"（本会话各出现多次，均被独立复核或实地核验抓出）

## 类型 1：假守卫（断言不可能变红）

| 实例 | 症状 | 修法 |
|---|---|---|
| HF 确定性断言 | 提交信息宣称已加断言，**补丁实际静默 no-op**；用例一直绿，而 L20 真的是确定性的 | 按**替换计数**校验补丁；做**反证**（把 `tail_draw` 改成 1 ⇒ 必须红） |
| "不存在回滚路径" | 断言"**没有**某条路径"——结论在写下时就已成立 ⇒ 永远 PASS | 改成**可枚举入口 + 故意移除守卫必须红** |
| "每段类型数 ≥2"（A 腿附录 E） | **先测量现状（已达标）再据此写断言** ⇒ 未来只可能"不变(PASS)"或"变多(仍 PASS)" ⇒ 永不会红 | 断言**实际编队构成**（"同时出现 ≥2 类型怪物的遭遇比例 ≥ 阈值"），阈值由基线实测写死 |

**判据**：写守卫前必须能回答——**"改坏哪一行会让它红？"** 答不出来 ⇒ 它不是守卫。

## 类型 2：先测量后断言（用现状给现状背书）

**症状**：把"当前数据满足 X"直接写成断言"必须满足 X"，于是守卫只保护现状、不保护设计目标。
**修法**：断言**设计目标**（编队/密度/占比等**行为量**），现状只用来**校准阈值**并记录为基线 ✓。

## 类型 3：没读准就断言（把设计意图当代码事实）

本会话 7 次被核验否证 ✗✓，例如：`dropItems` 当参数（实为函数内局部量）、以为单机无死亡掉落（实为**有**）、以为单机退出写档（实为**仅多人**）、以为无装备需求（实为有 `minStrength/minMagic/minDexterity`）、以为无 elixir（实为有，且**id 列为空、以 `miscId` 索引**）、把 `role` 列的 `-` 读成"非 core"（实为 pair 中另列的值）。
**修法（硬规则）**：
1. 任何"既有语义"的断言**必须带 `文件:行号` 或可执行命令**，否则不许写进规格/提交信息 ✓；
2. **未核验项显式标 ⚠ 并进"待实测"清单**，不得当事实使用 ✓；
3. **提交前对"提交信息里声称写入的每一处"做计数 grep** ✗（本会话出现过一次"提交信息宣称写入附录，实际写入因语法错中止"）；
4. 复核者（含子 agent）的主张**一律实地核验**：本会话既有"复核者主张被否证 2 次"，也有"复核者之间冲突由读码定谳 1 次"，还有"复核者抓对了方法、却算错了结论 1 次" ✓。

## 一条通用流程

**执行 → 独立复核 → 逐条实地核验 → 只采信被证实者 → 写回文档 → 记录失败** ✓
（复核**作业失败 ≠ 复核通过**：本会话 codex 两连产品级失败，按"未复核"处理并改派 ✓）
