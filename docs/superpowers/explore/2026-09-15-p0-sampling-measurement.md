# P0 实测：采样预算到底买到了什么（引擎内实测，2026-09-15）

> **性质**：实测数据 + 解读，**不是规格**。为「P0：采样与编组」的决策提供第一手数字。
> **方法**：新增的 test-only 测量套件（`test/sampling_behavior_test.cpp` 的 `SamplingBaselineTest.Measurement*`），**调用真实引擎** `GetLevelMTypes()`，未改任何生产代码。
> **复现**：`cd build && SAMPLING_REPORT=/tmp/p0.md ./sampling_behavior_test --gtest_filter='SamplingBaselineTest.Measurement*'`
> **环境**：本机 MPQ 为 `spawn.mpq` + `hellfire.mpq`（**无 `DIABDAT.MPQ`**）；`gbIsSpawn` 在测试上下文不可靠（见 P0-C）。

**解读**

1. **塌缩是真实的，且比既有诊断更靠前**：教堂 ~7 类 → 地狱 **3.2-3.3 类**；distinct AI 从 5.0-5.5 掉到 **3.0-3.1**；distinct 行为类别 4.3 → **2.5-2.8**。也就是说后期一层里，玩家面对的是**大约 3 种怪、3 套 AI、2-3 类行为**。
2. **Σ`image` 几乎顶到 4000**（后期 3523-3762，教堂 3829-3889）→ **预算是绑定约束**，不是 `MaxLvlMTypes=24`，也不是候选池不够（见 P0-B 的 candidates 列：后期仍有 9-16 个候选）。
3. **L16 是例外**：它走硬编码分支（`GetLevelMTypes` 在 currlevel==16 时预加 Advocate/RBlack/Diablo 后直接 return），预加**不经过预算**，所以 Σ`image`=6506 超出 4000。这解释了为什么"最后一层"反而比 13-15 层多。
4. 与探索阶段的 Python 模拟相比，本表是**引擎实测**：趋势一致（后期 3 类量级），个别层有差异（本表 L2=7.0 而模拟给 5.9），**以本表为准**。

（每格是**最好/最坏界**：按 image 从小到大 / 从大到小装入，不代表引擎的随机抽取结果；实际落在两者之间。）

**解读**

1. **预算是唯一值得掰的杠杆**：同一层里，4000→8000 让后期从 1-4 类变成 3-7 类；→12000 达到 5-9 类；→20000 时后期几乎吃满候选池（10-14 / 11-14）。
2. **候选池从不是瓶颈**：L3 有 24 个候选、L9-14 有 14-16 个，但 4000 只放得进 1-4 个。
3. **代价仍未量化**：预算提高的**内存代价**取决于 `image` 与真实字节的关系，而这一点没测出来（见 P0-C）——**这是改常量前必须先闭合的唯一实质未知**。

## P0-C：`image` 列 vs 真实精灵字节 —— **未决**

测量结果：22 个被实测到的类型，`sprite KiB` **全部为 0.0**，即 `OpenAsset("monsters\\<spritePath><animletter>" + DEVILUTIONX_CL2_EXT, size)` 在本环境没有解析到任何怪物精灵文件。

**未决原因（两种可能，尚未区分）**

1. **本机数据不含多数怪物精灵**：只有 `spawn.mpq`（shareware）+ `hellfire.mpq`，**没有 `DIABDAT.MPQ`**；但连 Zombie/Skeleton/Fallen（spawn 里应当存在）也是 0，所以这不像是全部原因。
2. **路径/扩展名约定与加载器不一致**：测试镜像的是 `monster.cpp:3224` 的 `FileNameWithCharAffixGenerator({"monsters\\", spritePath}, DEVILUTIONX_CL2_EXT, Animletter)`；本构建 `UNPACKED_MPQS=OFF`（`build/CMakeCache.txt`）→ 期望 `.cl2`。**尚未验证** MPQ 内实际条目名（大小写、目录分隔、扩展名）。

**为什么重要**：P0 的所有"改预算"方案都依赖"付出的内存是多少"。在 P0-C 闭合之前，**不应改 4000**。
**如何闭合**：用 `tools/mpqextract`（或 debugger/`LogVerbose`）列出 `DIABDAT.MPQ`/`spawn.mpq` 里 `monsters\` 下的真实条目名；或直接在测量套件里枚举候选路径变体（大小写 / 正反斜杠 / .cl2 vs .clx）打印成功项。需要一张 **retail `DIABDAT.MPQ`** 才能覆盖后期怪物。

## 对决策的三条直接含义

1. **"多几类怪"在当前预算下买不到**：后期一层只有 3.2 类，Σ`image` 已顶到 3523-3762/4000。加新怪物（image≈1000）会挤掉 1-1.5 个原类型——**与探索阶段 E5a 的"Δ 可能为负"一致，且现在有引擎实测支持**。
2. **固定预算下，唯一还有表达力的轴是"组合"**：既然只有 3 类怪、3 套 AI 进得来，那么"谁和谁一起出现、以什么队形出现"（已实现却未被普通散布调用的 `PlaceGroup` leader/leashed）就是当前**信息量最大**的改造点——它不增加 memory 成本，只改调用点。
3. **A1/A3 的量级预期应按下调**：一层只容 3.2 类，A1 的变体要先进池才可能被看到；A3 改的 2-3 只洞穴风筝还要与 B1 已生效的"洞穴 kite ≤2"竞争。**这不是否定 A1/A3，而是把它的验收改为"变体在采样后仍可见"**（框架 §2 已回写该反向依赖）。
