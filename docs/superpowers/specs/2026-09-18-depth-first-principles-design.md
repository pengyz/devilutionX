## 1. 问题陈述

**D1 的体验是一个自洽整体**（六件互相咬合）：两腔循环（城镇＝安全/经济/永久 ↔ 地牢＝危险/发现/**单程**）／单位＝一次**有限、持久、不可逆**的下降／信息未知但可学／准备有限且**在战斗内消耗**／低数量高杀伤的威胁／终局**合上**。

**业界缺少直接示例的原因**：没有人深化 D1 的设计，大家换成了 D2 的设计（无限、可重置、数值成长的跑步机）。

**判定**：D1 的"薄"**主要是实现面**，外加**两处设计面缺口**：

| D1 的薄 | 归类 | 核验锚点 |
|---|---|---|
| 高难度＝**HP×3 纯倍率** | 实现面 | `Source/monster.cpp:255` ✓ |
| 怪物**无群体行为** | 实现面（我们已开工） | `Source/monster.cpp:3054 PlaceGroup`／`:318 GetUniqueMonstPosition` ✓ |
| 主题房存在但**无控制** | 实现面 | `Source/levels/themes.cpp:349 PlaceThemeMonsts`／`:913 CreateThemeRooms` ✓ |
| 物品模型薄（无独立词缀字段） | 实现面 | `Source/items.h:204 _iMagical` ✓ |
| 信息/UI 停在 1996（已在补） | 实现面 | `Source/levels/gendung.cpp:327 CanTarget` ✓ |
| **① 存档不能兑现"不可逆"** | **设计面** | 见 §3/§4.1 |
| **② 信息/威胁只有单向** | **设计面（待裁决）** | 见 §4.2 |

### 1.1 设计层闭环审计（六结构 + 第七结构 × 两阶段）

**方法**：每个结构在前中期/后期各问四问——**有状态？有决策？有后果？有反制/恢复？** 四问全「有」才算**闭环**。

| 结构 | 前中期 | 后期 | 判定 |
|---|---|---|---|
| 两腔循环（城镇↔地牢） | ✓✓✓✓ | **金币不再是决策**（出口＝买/修/丢/取 `stores.cpp:2062/1482`、`control_gold.cpp:26`、`qol/stash.cpp:688` ✓；另有神殿出口 ⚠ 未核验） | 后期**未闭环** |
| 准备有限（腰带/卷轴/补给） | ✓✓✓✓ | **约束不再咬合**（`stores.cpp` 的 `HealPlayer` 提供免费治疗 ✓） | 后期**未闭环** |
| 信息未知但可学 | ✓✓✓✓ | ✓ | 闭环 |
| 单程下降 + 层持久 | ✓✓✓✓ | ✓（`diablo.cpp:3163` ✓） | 闭环 |
| 低数量高杀伤的威胁 | ✓✓✓✓ | 难度＝**纯倍率**（`monster.cpp:255` ✓）；**是否真被角色成长压过待实测** ⚠ | **待实测** |
| 终局合上 | — | ✓（**故意**如此） | 闭环 |
| **⑦ 持续消耗（本审计新增）** | ✓（补给 + 死亡代价） | **✗ 两者同时失效，且无第三种消耗替代** | **结构缺失** |

**结论（经两路独立复核修正 v3）**：缺口**不是三个并列项**，而是**一个**——**缺少"持续消耗"结构**（症状＝①金币失去决策作用 ②补给约束失效 ③威胁被成长压过）。
**且三者的共同地基是"死亡可撤销"**（单机死亡不写档 ✓；死亡时 ESC 一键读旧档 `diablo.cpp:524-532` ✓）⇒ **第 0 章（存档契约）是其前置条件**，而非并列项 ✓。

## 4. 方案

### 4.1 第 0 章：存档契约（**契约层**：只定契约点、语义、失败语义）

> **存档＝提交（commit） / 时间线唯一 / 死亡留痕 / 提交失败不得提供死前 Load**

| 条 | 内容（可观测语义，不指定函数） |
|---|---|
| **① 死亡提交** | 单机玩家死亡后，**受管存档中必须已存在"死亡态"**：掉落物在死亡地点、金币已扣、角色处于死亡/复活流程的持久状态。⇒ 读档/退出重开**不能**回到死前 ✗ |
| **② 切层提交** | 进入/离开关卡时的持久化语义与多人一致（单机已有 `pfile_save_level` ✓，其语义须明确为"包含当层进展"） |
| **③ 时间线唯一** | **不提供**任何回滚到已提交死亡态的入口 ✗（无开关 ✓） |
| **④ 死亡不终结角色** | 死亡后可复活继续 ✓；"留痕"＝**装备/金币损失 + 尸体位置**，**不是删档** ✓（`MyPlayerIsDead` 复活即清除 ✓） |
| **⑤ 提交失败的语义（硬要求）** | 提交必须"**先持久化死亡意图，再原子替换完整存档**"；**中断/失败后启动时若发现未完成的死亡意图 ⇒ 禁止加载旧档**（进入死亡态或新局）✓；**不得**出现"死亡已发生但旧档仍可加载" ✗ |
| **⑥ 边界** | 契约只约束**应用内受管存档路径** ✓；**外部复制/替换存档文件不受约束**（显式声明 ✓） |
| **⑦ 多人** | **无变化** ✓（其写档与死亡语义已存在 ✓） |
| **⑧ 旧档** | 存活的旧档可继续使用 ✓；新语义**从下一次死亡起**适用 ✓；升级前未提交的死亡**不可追溯** ✓；**不做格式迁移** ✓（引用决策 34/35 ✓）+ 一次性契约提示 ✓ |

**为什么不是"新增规则"**：死亡掉落在**单机本来就有** ✓，多人**本来就写档** ✓ ⇒ 本契约 = **把单机补成与多人同一语义 + 给提交加原子性**，零新概念 ✓。

### 4.2 缺口 ②：信息/威胁的双向性（**只登记，待裁决**）

**v2 把判据改为可判定**（v1 的"一局内可学、不记数字"不可判定 ✗）：
> 判据：该交互必须能用**一句"如果 X 则 Y"**描述，且 **X、Y 都是既有 UI 元素或既有概念**；并且**必须做对照实验**（对照法见试玩协议：同种子 A/B + 强制选择）。
> **反例警戒**：光照压制当年也被认为"可行动"，最终因**无反制**被撤销（宪章 §6 记录）⇒ "直观可学"**不足以**避免 DP2 违规 ✗。
