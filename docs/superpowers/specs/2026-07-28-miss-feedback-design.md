# 未命中反馈

**日期**：2026-07-28
**分类**：Base
**状态**：已批准
**评判基准**：`2026-07-27-better-d1-design-charter.md`

---

## 1. 问题陈述

D1 的命中判定是隐藏的 roll，且失败时**没有任何反馈**。玩家攻击怪物、动画播完、怪物没掉血，游戏不告诉他发生了什么。

具体症状（可复现的代码路径）：

| 位置 | 分支 | 当前行为 |
|---|---|---|
| `Source/player.cpp:552` | `if (hit >= hper) { return false; }` | 近战未命中，静默返回 |
| `Source/missiles.cpp:306` | `if (hit >= hper) { return false; }` | 远程与法术未命中，静默返回 |

两处结构完全相同：`hit = GenerateRnd(100)`，`hper` 由攻击者命中属性减去目标护甲后 `clamp(5, 95)`，`hit >= hper` 即未命中。

这属于宪章第 2 节三分法中的**错误设计**：本意是让装备的命中属性有价值，但玩家收不到反馈，无法把「打不中」与「命中不足」联系起来，那份价值感就没有传达。玩家的合理反应是以为自己点错了目标，或者以为游戏卡了。

按支柱 B1 的判定问法——玩家能通过游戏内的什么行动知道这件事？答案是「无」。命中率既不显示在角色面板，也不在战斗中体现。唯一途径是查 wiki 或打上千次凭感觉估算。这正是 B1 要求消除的那类未知。

这也是宪章第 1 节评估「现代玩家可接受度」时找到的**唯一一项既提升可接受度、又不与 D1 独特性冲突的改动**——其余障碍（地牢内不能跑、单键攻击、死亡掉装备、退出重进怪物重置）按三分法均属独特性，改了 D1 就不是 D1。

## 3. 事实基础

均于 2026-07-28 核实。

### 命中判定

| 事实 | 值 | 出处 |
|---|---|---|
| 近战未命中分支 | `if (hit >= hper)` → `return false` | `Source/player.cpp:552`，函数 `PlrHitMonst`（`:528`） |
| 远程与法术未命中分支 | 同上 | `Source/missiles.cpp:306`，函数 `MonsterMHit`（`:282`） |
| 命中 roll | `GenerateRnd(100)` | `Source/player.cpp:542`、`Source/missiles.cpp` 同函数内 |
| 命中率钳制范围 | `std::clamp(hper, 5, 95)` | `Source/player.cpp:549`、`Source/missiles.cpp:297` |
| 现有 miss 反馈 | **无**。`player.cpp`、`monster.cpp`、`floatingnumbers.cpp` 中不含 miss 相关字符串 | grep 无匹配 |

`PlrHitPlr`（`player.cpp:702`）是 PvP 路径，本规格不覆盖——PvP 的反馈需求与单人不同，且改动会影响多人同步，留待需要时单独立项。

### 浮动数字系统的现状

| 事实 | 值 | 出处 |
|---|---|---|
| 接口 | `void AddFloatingNumber(Point pos, Displacement offset, std::string text, UiFlags style, int id = 0, bool reverseDirection = false)` | `Source/qol/floatingnumbers.h:17` |
| C++ 侧生产调用者 | **零**。只有 `ClearFloatingNumbers()` 在 `gamemenu.cpp:301` 与 `diablo.cpp:3423` 被调用 | grep |
| 唯一调用者 | Lua 模块 `devilutionx.floatingnumbers` | `Source/lua/modules/floatingnumbers.cpp:18` |

上游有一套完整的浮动数字渲染系统（渲染、动画、生命周期），但游戏本身从不使用它，只暴露给 Lua。这解释了为什么 D1 没有伤害数字显示。

选择直接从 C++ 调用而非走 Lua 事件：`AddFloatingNumber` 声明在公开头文件 `Source/qol/floatingnumbers.h` 中而非匿名命名空间，是上游有意暴露的 C++ 接口，只是上游自己未使用。走 Lua 事件会让本特性变成可选 mod 而非内建行为，那就不再是 Base 层特性。

## 4. 方案

在两处未命中分支各增加一次 `AddFloatingNumber` 调用，显示在**目标怪物头上**——玩家关心的是「我打这个目标没打中」，而非「我这次挥空了」。

文本为 `_("Miss")`，走 `gettext` 以支持本地化。

不新增选项开关。理由：宪章底座层红线 7 要求不代替玩家做选择，红线 8 要求不移除玩家已有的选项——增加一个反馈不涉及任何一条。而每个特性都配一个开关会产生宪章第 1 节反对的「设置汤」。若将来证明有人想关掉，那时再加。

不覆盖 PvP（`PlrHitPlr`），见第 3 节。

### 调用真实触发的证据

第 6 节标注为「无法机械验证」的那一项，实际用探针取得了硬证据。

在 `player.cpp` 的反馈调用后临时插入 `fprintf(stderr, "PROBE_MISS_MELEE\n")`，重建 `timedemo_test` 并运行 `WarriorLevel1to2`：

**近战未命中触发 12 次。**

这同时证明了两件事：

1. 反馈调用在真实游戏循环中确实被执行，不是死代码
2. **调用不扰动游戏状态**。timedemo 会把运行结果与参考存档逐字段比对，任何 RNG 消耗或状态改变都会导致发散。它通过了，因此 `AddFloatingNumber` 对游戏状态是无副作用的——这正是红线 5「不改变战斗结果」所要求的，且比阅读代码更可靠

探针已撤除，撤除后复验构建与 651 项测试均通过。

远程分支（`missiles.cpp`）未取得同类证据：`WarriorLevel1to2` 是战士近战流程，不触发远程命中判定。该分支与近战侧代码结构完全相同、调用同一函数，但**其触发未经实证**。
